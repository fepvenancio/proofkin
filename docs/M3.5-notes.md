# Milestone 3.5 notes: harder fixed cases, two-slot tokens

Not in PLAN.md's milestone table. It came out of a review of the contracts before launch: the notes of
milestones 1 and 3 had already flagged that "solved" is only 10 trials, and a measurement showed how much
that lets through. The contracts are immutable once deployed, so it was done before milestone 5.

## What changed

| Puzzle | Fixed trials before | Fixed trials now | Trials a solution must pass |
|---|---|---|---|
| QUORUM7 | all 0 with t=7; all 1 with t=1 | all 0 with t=1; all 1 with t=7 (each exactly on the threshold, one from each side) | 10 |
| MEDIAN5, FAIR_SPLIT4 | 2 | unchanged | 10 |
| SORT8 | 2 | + 2 permutations (trials 10, 11) | 12 |
| GRID_PATH | 2 | + 6 (trials 10..15): each monotone path in turn is the single cheapest | 16 |
| KNAPSACK3 | 2 | + 6 (trials 10..15): each single item, then each pair, is the unique best set, weighing exactly the cap | 16 |

- **`Token` is two storage slots, not three.** `seed` is slot 0 on its own; the pointer and the six small
  fields (26 bytes) share slot 1. Declaring the 20-byte pointer first had wasted a slot, because a 32-byte
  seed cannot share one. The `tokens(id)` getter now returns `(seed, program, ...)`; the generated ABI
  follows it.
- **Trial layout.** Trials 0 and 1 stay fixed, 2..9 stay random with the same inputs, so the renderer's
  node values (trial 2) and every SVG snapshot are untouched. The further fixed cases sit at trial 10 and
  up. A trial past a puzzle's own list is random again, so `inputs()` is defined for every trial index.
  `trialCount(puzzleId)` (Solidity `Puzzles.trialCount`, TypeScript `trialCount`) is the number a solution
  must pass.
- **Wrong programs as fixtures.** `packages/vm/src/cheats.ts` builds 42 valid programs, each a correct
  solution with one thing left out (ignore a QUORUM7 voter, compare with `>` or `t - 1`, miss one GRID_PATH
  path, forget one KNAPSACK3 subset or use `<` on the capacity, drop one SORT8 comparator). They are
  written to `fixtures/cheats.json` by `pnpm gen:fixtures`. With nothing left out each builder makes a
  correct solution (tested), so a cheat is exactly one omission from a program that may mint.
- **Differential vectors** now span trials 0..17 (`diff.json` is 136 KB larger): every trial any puzzle has,
  plus two past the end, which are random again.
- PLAN.md §2, §4.1, §5.1, §5.2, §7 and §9 say so. The playground lists every fixed case on the puzzle
  page, runs all of them in "Test locally", and names the failing one by what it is.

## Why: what the old fixed cases let through

Pass rate of a wrong program: the share of 5,000 random seeds on which it passes every trial. The inputs are
the real ones (the TS port, differentially tested against the Solidity). "Best of 5 salts" is a committer who
tries five commits of the same program and reveals the one whose seed lets it through.

| Wrong program | Before | After | Before, best of 5 salts |
|---|---|---|---|
| QUORUM7 ignores any one voter | 54 to 55% | 0% | 98% |
| QUORUM7 compares with `>` / with `t - 1` | 29% | 0% | |
| GRID_PATH misses one path | 20 to 32% | 0% | 67 to 86% |
| KNAPSACK3 forgets one pair / one single item | 38% / 47 to 48% | 0% | |
| KNAPSACK3 uses `<` on the capacity | 42% | 0% | |
| SORT8 without the comparator (1,4) or (3,6) | 30% | 0% (checked for all 19 removals) | 83% |

Already caught by the random trials, and still: ignoring any one GRID_PATH edge, leaving a request out of
FAIR_SPLIT4's total, dropping any early SORT8 comparator, two simple MEDIAN5 mistakes.

The reasoning behind the choice of cases: the reward for a wrong program is a smaller node count, so the
cheats that matter leave work out. Each new case makes one such omission fail on every seed: a case where
that voter, path, subset or comparator decides the answer.

## Gas

`reveal` for each fixture solution (`test_revealGasPerFixture`):

| Puzzle | Before | After | Change |
|---|---|---|---|
| QUORUM7 | 564,184 | 542,791 | -21,393 |
| MEDIAN5 | 512,065 | 490,672 | -21,393 |
| SORT8 | 1,068,817 | 1,177,900 | +109,083 |
| GRID_PATH | 771,300 | 1,015,541 | +244,241 |
| KNAPSACK3 | 899,705 | 1,209,013 | +309,308 |
| FAIR_SPLIT4 | 606,341 | 584,948 | -21,393 |

The saving on every mint is the storage packing. The extra cases cost about 44k each on GRID_PATH, 55k on
KNAPSACK3, 65k on SORT8. The worst case is now KNAPSACK3 at 1.21M gas, up from SORT8's 1.07M.

## How it was checked

Written test-first; each test below failed before the change.

- Against the old fixed cases, **29 of the 42 wrong programs got past** the fixed trials; only the 13 that
  trials 0 and 1 already caught failed (SORT8 comparators 0 to 11 and KNAPSACK3 without the full set).
- `Cheats.t.sol`: every cheat is a valid program; every one fails a fixed trial; none can be minted
  through the real `commit` / `reveal`; and a fuzz test commits a random cheat under a random salt, so a
  random seed, and expects `SolveFailed`.
- Property tests that the new cases are what they claim: each GRID_PATH case has exactly one cheapest path,
  each KNAPSACK3 case a unique best set at exactly the cap, the SORT8 cases are permutations of eight
  distinct values (Solidity and TypeScript both).
- `test_aTokenFillsExactlyTwoStorageSlots` reads the getter's storage accesses and checks the two slots.
- Existing tests that looped to `Puzzles.TRIALS` stayed green but would have stopped checking the new cases;
  they now loop to `trialCount` (the solutions, the invariant handler, `_firstFailingTrial`, the
  stored-seed replay).
- **Tests:** Solidity 196 (was 185), `packages/vm` 386 (was 204), playground 148 (was 144). Slither 0 High,
  0 Medium, 0 Low (the same three informational detectors as before); coverage of `src/` 100% of lines,
  99.8% of statements, 98.8% of branches.
- **Mutation testing:** 11 new mutants. In the `vm` suite (judged by the differential vectors alone): the
  QUORUM7 pair reverted, the SORT8 cases or the last GRID_PATH / KNAPSACK3 case dropped, trials past a
  puzzle's own treated as fixed, and three corrupted table entries. In `proofkin`: the contract running only
  the original 10 trials. In the playground: three (a trial from 10 up called random, random cases numbered
  without skipping fixed ones, the local test skipping the further cases). Two old patterns stopped matching
  and were rewritten: "only two trials checked" and the playground's message threshold. "The further fixed
  trials are never run" is caught only by `Cheats.t.sol`, which is why that test is a stage of the
  `proofkin` suite.
  All four suites were then run in full: **83 mutants, none survived** (`vm` 17, `proofkin` 35,
  `renderer` 7, `playground` 24), and a hash comparison afterwards showed every source file back
  byte for byte. The machine was loaded by other projects during that run, and the playground stage counts
  any failing test, a timeout included, as a kill. So the four new playground mutants were also applied by
  hand: each fails the assertion meant for it, with no timeout.

## What this does not fix

- **Grinding is still possible** for any wrong program that gets through all the fixed cases and is lucky
  on the 8 random ones. The cheats above are mine; the fixed cases remove the families I could construct,
  not every wrong program. In particular a bug in how a program reads its inputs is caught by the random
  trials alone: a GRID_PATH "greedy walk" passes 0.5% of seeds, 2.5% with five salts, before and after.
  Making an abandoned commit cost something (escrow at `commit`) is still the owner's call.
- **Variants of one solution still mint as separate tokens** (swapped operands, reordered nodes).
- **The SORT8 cases are tailored to the 19-comparator odd-even merge network.** Another correct network
  has different weak spots; only single-comparator removals of this one were checked, exhaustively.
- **MEDIAN5 and QUORUM7 had holes, found after this milestone and closed in milestone 3.6** (see "Found
  afterwards" below). I had tried only two simple MEDIAN5 mistakes and called it fine; that was too little testing.
- FAIR_SPLIT4 was tried only with "leave one request out", which is caught; a later search found six
  other bypasses that get through on about 0.1% of seeds.
- Nothing is deployed, so no contract was redeployed or migrated.

## Found afterwards

A systematic search (bypass each node of each fixture solution in turn, drop what is left dead, measure how
often the wrong program passes every trial; `scratchpad` script, not in the repo) and exact enumeration of
QUORUM7's inputs, run while reviewing a second opinion:

| Puzzle | What still gets through | How often |
|---|---|---|
| MEDIAN5 | 14 of 20 one-node bypasses of the 15-node solution (13 and 14 nodes), e.g. `hi = MAX a b` replaced by `b` | 6 to 17% of seeds per commit |
| QUORUM7 | a program that reads only one voter (the playground's own 1-node starter), or the majority of three, or the majority of all seven ignoring `t` | 1.1%, 1.9%, 3.4%; `sum >= min(t,4)` 22% |
| FAIR_SPLIT4 | six bypasses (20 nodes) | about 0.1% |
| SORT8, GRID_PATH, KNAPSACK3 | two SORT8 bypasses | 0.07%; the rest are caught on every seed |

Why: QUORUM7's two fixed cases are unanimous (every vote the same), so any program that reads one voter passes
both, and MEDIAN5's two cases both have `x2` as the median. Sized fixes, not made: QUORUM7 + 7 cases (each
voter alone says yes with t=1) + 1 (six yes, one no, t=7) closes every QUORUM7 program I tried, and the review's
"six yes, one no, t=6" rotations alone close only the single-voter one. MEDIAN5 + 3 permutations
(`[40,120,80,160,200]`, `[160,40,200,120,80]`, `[120,160,40,80,200]`) close all 20 bypasses. **Closed in
milestone 3.6** ([M3.6-notes.md](M3.6-notes.md)).

## Environment note

`pnpm test:ts` runs the vm and playground suites in parallel. While another project's Hardhat test and
`forge build` kept this machine at a load average of 14 to 17, that command timed out in a different test on
each of two runs (vitest's 5 s default on the vm suite, 60 s on the playground's chain tests). Run one
after the other, with the load unchanged, both suites passed (386 and 148). No test was changed for this.
